# LedgerLens Domain Model and Database Schema V1

_Status: Proposed for review — do not implement until AR-0/AR-1 findings are considered_

_Last updated: 2026-07-17_

## 1. Purpose

This document defines the proposed clean domain model and Room database version 1 for the LedgerLens reset.

It replaces the prototype model rather than migrating from database versions 1–5. The application has not shipped, so prototype data is disposable. This proposal is designed to make the following distinctions explicit:

- an imported SMS message is not automatically a financial transaction;
- a sender is not the same thing as an account;
- parser output is not the same thing as user-confirmed truth;
- transaction treatment is not the same thing as spending impact;
- category is not transaction treatment;
- a reusable rule is not a direct database mutation;
- message deduplication is not the same thing as real-world event deduplication.

## 2. Scope and declared MVP assumptions

### Included

- Android local-first storage;
- inbound SMS messages;
- sender-level financial-source confirmation;
- optional account candidates beneath a sender;
- parser-owned transaction facts;
- explicit user overrides;
- typed review reasons;
- categories and merchant defaults;
- declarative rules with deterministic precedence;
- signed spending-contribution calculation;
- import-run status and recovery information.

### Deliberately limited

- US English and USD are the initial supported parsing scope;
- one Android application module;
- no cloud sync;
- no bank API aggregation;
- no automatic general-ledger/accounting model;
- no multi-user household support;
- no promise of recognizing every financial SMS format;
- no production migration from the prototype schema.

The schema stores ISO currency codes and locale-neutral minor units so future currency support does not require replacing the core transaction table.

## 3. Non-negotiable invariants

1. **Source confirmation gate**
   - A message from an unconfirmed source may be analyzed for preview.
   - It must not create an effective Activity transaction or contribute to Insights until the source is identified.

2. **Parser ownership versus user ownership**
   - Parser-owned facts may be regenerated by a new parser version.
   - User-owned overrides must survive reprocessing.

3. **Positive amount storage**
   - Monetary amount is stored as a non-negative minor-unit magnitude.
   - Account-flow direction and spending effect are separate typed fields.

4. **No silent financial rewriting**
   - DAOs persist/query data only.
   - Rules are evaluated by a domain service.
   - A rule never overwrites transaction-specific user overrides.

5. **Deterministic effective value**
   - Given the same parsed facts, user overrides, active rules, merchant default, and source/account state, the effective transaction must be identical.

6. **No duplicate message ingestion**
   - A durable unique ingestion fingerprint prevents the same SMS record from being inserted repeatedly.

7. **No false promise of event deduplication**
   - Different SMS messages may describe the same real-world event.
   - Such events are flagged or linked; they are not discarded solely because their values look similar.

8. **Financial totals are explainable**
   - Every included, excluded, or negative spending contribution must be explainable by treatment, spending effect, user override, or rule provenance.

## 4. Domain types

The names below are domain names. Room may store them as stable strings through converters.

### 4.1 SourceChannel

```kotlin
SMS
```

The enum exists even with one initial value so source identity does not become inseparable from SMS-specific naming.

### 4.2 SourceStatus

```kotlin
CANDIDATE
IDENTIFIED
IGNORED
```

- `CANDIDATE`: detected sender awaiting a user decision.
- `IDENTIFIED`: approved financial source eligible for transaction creation.
- `IGNORED`: not a financial source or intentionally excluded.

Do not represent this with combinations of `userConfirmed` and `ignored` booleans.

### 4.6 TransactionTreatment

```kotlin
PURCHASE
FEE
INCOME
TRANSFER
CREDIT_CARD_PAYMENT
REFUND
REVERSAL
REIMBURSEMENT
CASH_WITHDRAWAL

```

Treatment identifies what the financial event appears to be. It does not directly encode whether or how it affects spending.

### 4.7 MoneyDirection

```kotlin
DEBIT
CREDIT
NONE
UNKNOWN
```

- `DEBIT`: value moved out of the referenced account.
- `CREDIT`: value moved into the referenced account.
- `NONE`: informational event with no account movement.
- `UNKNOWN`: parser could not determine direction.

### 4.8 SpendingEffect

```kotlin
INCREASE
DECREASE
NONE
UNRESOLVED
```

The effective spending contribution is derived as:

```kotlin
when (spendingEffect) {
    INCREASE -> amountMinor
    DECREASE -> -amountMinor
    NONE -> 0L
    UNRESOLVED -> 0L // and requires review
}
```

The amount stored in the transaction remains non-negative.

### 4.9 Default treatment-to-spending mapping

| Treatment | Default spending effect | Notes |
|---|---|---|
| `PURCHASE` | `INCREASE` | Ordinary consumption. |
| `FEE` | `INCREASE` | Bank/service fee is spending. |
| `REFUND` | `DECREASE` | Reduces spending; merchant/category linkage may be incomplete. |
| `REVERSAL` | `DECREASE` | Reduces previously recognized spending when appropriate. |
| `REIMBURSEMENT` | `DECREASE` | Reduces spending if classified as reimbursement rather than income. |
| `INCOME` | `NONE` | Account inflow, not negative spending. |
| `TRANSFER` | `NONE` | Movement between owners/accounts, not consumption. |
| `CREDIT_CARD_PAYMENT` | `NONE` | Avoids counting card purchases and the later payment twice. |
| `INFORMATIONAL` | `NONE` | No spending event. |
| `CASH_WITHDRAWAL` | `UNRESOLVED` | Withdrawal may represent cash transfer or practical spending; user policy/review is required. |
| `UNKNOWN` | `UNRESOLVED` | No automatic contribution. |

This mapping is policy and must be covered by tests. A user or higher-precedence rule may override the spending effect.

### 4.10 ReviewDisposition

```kotlin
OPEN
RESOLVED
DISMISSED
```

- `OPEN`: unresolved review reasons remain.
- `RESOLVED`: user confirmed/corrected the transaction.
- `DISMISSED`: user intentionally leaves the transaction out of normal review flow.

Automatic review reasons are derived separately and are not represented by one string status.

Room entities must not be passed directly to UI.

### Core domain objects


### EffectiveTransaction

`EffectiveTransaction` is computed by the domain layer. It combines:

1. immutable message identity;
2. latest parser-owned facts;
3. active rule results;
4. merchant default;
5. transaction-specific user override;
6. review disposition and reasons;
7. provenance explaining each effective field.

It is not necessarily stored as a separate table in V1. Avoiding an effective snapshot prevents stale duplicated truth. Queries may join entities and compute effective values in a repository/use case. If performance later requires materialization, add it with explicit invalidation and reconciliation tests.

Fingerprint specification:

```text
v1 | channel | normalized sender | provider timestamp | provider type | normalized full body
```

Hash with SHA-256. Include a version prefix so normalization can evolve without silently changing semantics.

The fingerprint protects message ingestion. It does not prove two different messages describe different financial events.

#### Raw-body retention

V1 implementation must choose and document one policy before beta:

- retain locally until user deletion;
- configurable retention window;
- delete after successful parse while retaining fingerprint and redacted preview.

The schema permits `rawBody` to become null after retention cleanup. Parsers and Review must handle that state.

## 8. Effective-value precedence

Effective fields are resolved independently. A higher-precedence source can override one field without suppressing valid lower-precedence values for other fields.

### Proposed precedence, highest to lowest

1. transaction-specific user override;
2. explicit user exception rule;
3. source/account-scoped user rule;
4. merchant profile default;
5. parser-specific trusted rule/strategy result;
6. generic parser result;
7. unresolved/null.

For each field, resolution returns:

```kotlin
EffectiveValue<T>(
    value: T?,
    provenance: ValueProvenance,
    confidence: Double?,
    explanation: String?
)
```

### Rule conflict behavior

- higher priority wins within the same precedence level;
- equal-priority conflicting rules produce `RULE_CONFLICT` and do not silently choose based on database row order;
- the selected transaction-specific override always wins;
- a rule may fill an absent field without overriding a stronger field;
- rule evaluation order must be stable and tested.

## 9. Review derivation

Review reasons are derived from source/message state, parsed facts, effective values, evidence, and duplicate detection.

Example policy:

```text
source not identified                  -> SOURCE_UNCONFIRMED
message unsupported                    -> UNSUPPORTED_MESSAGE
message failed                         -> PARSE_FAILED
multiple plausible amounts             -> MULTIPLE_AMOUNT_CANDIDATES
no effective amount                    -> AMOUNT_MISSING
unknown effective treatment            -> TREATMENT_UNKNOWN
unknown direction where required       -> DIRECTION_UNKNOWN
UNRESOLVED spending effect              -> SPENDING_EFFECT_UNRESOLVED
purchase with no merchant              -> MERCHANT_MISSING
spending contribution with no category -> CATEGORY_MISSING
confidence below policy threshold      -> LOW_CONFIDENCE
several account candidates match       -> ACCOUNT_AMBIGUOUS
rule conflict                          -> RULE_CONFLICT
similar financial event detected       -> POSSIBLE_DUPLICATE_EVENT
```

A user’s `RESOLVED` disposition means they accepted or corrected the current effective result. If a later parser/rule change materially changes a reviewed field, the domain layer may reopen review with a reason such as `RULE_CONFLICT` or a future `MATERIAL_CHANGE_AFTER_REVIEW` reason.

## 10. Spending and reconciliation examples

### Example A — Ordinary month

| Event | Amount | Treatment | Spending effect | Contribution |
|---|---:|---|---|---:|
| Grocery purchase | $100 | PURCHASE | INCREASE | +$100 |
| Monthly account fee | $3 | FEE | INCREASE | +$3 |
| Store refund | $20 | REFUND | DECREASE | -$20 |
| Transfer to savings | $500 | TRANSFER | NONE | $0 |
| Credit-card payment | $300 | CREDIT_CARD_PAYMENT | NONE | $0 |
| Salary deposit | $2,000 | INCOME | NONE | $0 |

**Monthly spending:** `$100 + $3 - $20 = $83`.

### Example B — Unknown cash withdrawal

| Event | Amount | Treatment | Spending effect | Contribution |
|---|---:|---|---|---:|
| ATM withdrawal | $60 | CASH_WITHDRAWAL | UNRESOLVED | $0 pending review |

The Review flow asks whether this should count as spending, be treated as a transfer to cash, or use a saved user policy.

### Example C — Reversal pair

| Event | Amount | Treatment | Spending effect | Contribution |
|---|---:|---|---|---:|
| Temporary purchase authorization | $45 | PURCHASE | INCREASE | +$45 |
| Reversal | $45 | REVERSAL | DECREASE | -$45 |

Net contribution is `$0`. If a later posted purchase arrives, duplicate-event detection must prevent the authorization/posting combination from becoming unexplained double spending.

### Example D — User override survives reparse

1. Parser V1 sets merchant `WM SUPERCENTER`, category null, treatment PURCHASE.
2. User sets merchant `Walmart`, category `groceries`, and resolves review.
3. Parser V2 reparses the message and improves parsed merchant to `Walmart Supercenter`.
4. Effective merchant remains user override `Walmart`; effective category remains `groceries`.
5. Parser-owned evidence/version updates without changing the override row.

## 11. Ingestion and processing state machine

### Import coordinator

```text
START
  -> READ_PROVIDER
  -> NORMALIZE_AND_FINGERPRINT
  -> INSERT_MESSAGES_IDEMPOTENTLY
  -> UPSERT_SENDER_SOURCES
  -> MARK_SOURCE_CONFIRMATION_GAPS
  -> PARSE_MESSAGES_FOR_IDENTIFIED_SOURCES
  -> EVALUATE_RULES
  -> DERIVE_REVIEW_REASONS
  -> UPDATE_IMPORT_RUN
  -> COMPLETE / PARTIAL_FAILURE / FAILED
```

### Idempotency rules

- inserting an existing `ingestionFingerprint` is a no-op and increments duplicate count;
- re-running source detection updates detector-owned suggestions but preserves source user status/name;
- re-running the parser updates parser-owned transaction fields only;
- re-running rule evaluation does not write bulk field changes into transactions;
- re-running review derivation preserves explicit user overrides and disposition unless a material conflict requires reopening.

## 12. DAO boundaries

### SourceDao

- insert/upsert detector-owned source fields while preserving user-owned fields;
- observe/get sources;
- update source status and user label;
- no transaction mutation.

### AccountDao

- upsert account candidates;
- update account status/user label;
- query accounts by source;
- no transaction mutation.

### SmsMessageDao

- batch insert with ignore-on-unique-conflict;
- query processable messages by state/source/date;
- update processing state/error/attempt count;
- delete body according to retention policy;
- no parser or rule logic.

### TransactionDao

- upsert parser-owned transaction facts by message ID;
- observe/query transactions and relevant joins;
- no direct merchant/category/rule bulk rewrites.

### TransactionOverrideDao

- upsert/delete one transaction-specific override;
- update review disposition;
- no parser-owned field changes.

### CategoryDao

- query active hierarchy;
- create/update/deactivate user categories.

### MerchantProfileDao

- query/upsert merchant profiles and defaults.

### TransactionRuleDao

- persist/query/activate/deactivate rules;
- no updates to transaction rows.

### ImportRunDao

- create and update run state/counts;
- query latest run and interrupted runs.

Multi-table workflows use `withTransaction` in repositories/use cases.

## 17. Required V1 tests

### Financial semantics

- purchase increases spending;
- fee increases spending;
- refund/reversal/reimbursement decrease spending;
- transfer/card payment/income/informational contribute zero;
- cash withdrawal and unknown remain unresolved by default;
- transaction override changes spending effect predictably;
- monthly and category totals reconcile.

### Data ownership

- parser rerun does not overwrite transaction override;
- source detector rerun does not overwrite user source status/name;
- merchant default does not override transaction override;
- disabling a rule restores lower-precedence effective values;
- equal-priority conflicts create review reason.

### Integrity

- duplicate ingestion fingerprint is rejected/ignored;
- one message has at most one parser transaction;
- deleting imported data cascades messages/transactions/overrides;
- deactivating category preserves historical references or safely yields uncategorized effective state;
- account removal sets optional transaction references to null;
- full reset is transactional.

### Time

- month boundaries use explicit timezone;
- DST transitions do not move a transaction into the wrong reporting period;
- injected Clock controls created/updated timestamps in tests.

### Duplicate events

- authorization/posting pair can be marked possible duplicate;
- reversal pair is not deduplicated as an identical message;
- two-sided transfer does not create spending contribution;
- similar legitimate purchases are not automatically discarded.

## 18. Open decisions for AR-1

1. Should raw SMS bodies be retained indefinitely, time-limited, or deleted after successful parse?
2. Is database encryption required for MVP beta, and which mechanism is maintainable with Room/KSP?
3. Should account profiles be user-visible in MVP or remain an internal attribution detail initially?
4. Should CASH_WITHDRAWAL default to `UNRESOLVED`, `NONE`, or a user-configurable global policy?
5. Should a reviewed transaction automatically reopen when a lower-level parser field changes but effective user-owned fields remain unchanged?
6. Should merchant defaults permit treatment/spending-effect changes, or category only in the initial release?
7. Does `transaction_rules` need a separate normalized action table, or are validated typed nullable action columns acceptable for V1?
8. Should possible duplicate-event state be persisted explicitly or derived from `eventFingerprint` and evidence?
9. Should the three-destination MVP navigation defer Insights until sufficient data exists?
10. What distribution channel must the `READ_SMS` feature satisfy?

## 19. Acceptance criteria for approving this proposal

The proposal is ready for implementation only when:

- AR-0 independent review has no unresolved blocker/high findings relevant to the model;
- AR-1 reviewers agree that spending totals reconcile across the documented examples;
- parsed facts and user overrides remain separately owned;
- source and account identity support one sender with several accounts;
- rule behavior is deterministic and non-destructive;
- duplicate message and duplicate event concepts are separate;
- privacy/retention decisions are explicitly assigned to a phase and owner;
- the first implementation slice can remain runnable throughout the migration.
